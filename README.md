# 📚 Подробное Руководство Разработчика (Developer Guide)

Добро пожаловать в проект! Этот документ — ваш главный путеводитель по архитектуре, коду и бизнес-логике приложения по подбору автозапчастей. Он написан так, чтобы даже начинающий разработчик смог легко разобраться в том, как всё устроено.

## 🛠 1. Используемые Технологии (Стек)

Наше приложение разделено на две независимые части: **Frontend** (то, что работает в браузере) и **Backend** (то, что работает на сервере).

### Frontend (Клиентская и Админская части)
Мы не используем тяжелые фреймворки (типа React или Angular). Все написано на базовых технологиях Интернета:
* **HTML5** — разметка и структура интерфейса.
* **CSS3** — стили, цвета, анимации и верстка (адаптивность через flexbox/grid).
* **Vanilla JavaScript (JS)** — "чистый" язык программирования браузера для логики (нажатия кнопок, отправка данных на сервер).

### Backend (Серверная часть)
* **Python 3** — основной язык программирования.
* **FastAPI** — очень быстрый современный веб-фреймворк для создания API. Он автоматически генерирует документацию.
* **SQLAlchemy** — ORM (Object-Relational Mapping). Библиотека, позволяющая работать с базой данных, используя объекты Python вместо написания сырых SQL-запросов.
* **Pydantic** — библиотека для строгой проверки данных (чтобы вместо текста не прислали число). Встроена в FastAPI.
* **PostgreSQL** — мощная и надежная база данных (используется на сервере Render).

## 🗄 3. База Данных и Архитектура (models.py)

В файле `backend/app/models.py` описана структура всех таблиц. Благодаря SQLAlchemy мы пишем классы Python, а библиотека сама переводит их в таблицы базы данных.

### Главные Таблицы (Классы):

1. **`Client` (Клиенты)**
   * **Поля:** Имя, Телефон, Email, `hashed_password` (зашифрованный пароль), `auth_token` (уникальный ключ сессии), `is_verified` (подтвержден ли телефон/email).
   * **Суть:** Это главная учетная запись. К ней привязываются машины, запросы и заказы.

2. **`Car` (Автомобили)**
   * **Поля:** `vin`, `brand`, `model`, `engine_code`, `mileage` и др.
   * **Связи:** У авто есть `owner` (владелец - `Client`). Машина может менять владельца. К авто привязываются заказы.

3. **`OrderRequest` (Запросы на подбор)**
   * **Суть:** Когда клиент нажимает "Нужны тормозные колодки", создается этот запрос.
   * **Связи:** Привязан к клиенту (`client_id`) и машине (`car_id`).

4. **`Proposal`, `ProposalItem`, `ProposalAlternative` (Сметы / Кошториси)**
   * **Суть:** Ответ менеджера на запрос клиента. 
   * **Структура:** Смета (`Proposal`) состоит из деталей (`ProposalItem`, например, "Масло"). У каждой детали есть варианты выбора (`ProposalAlternative`, например, "Motul за 1000 грн" или "Elf за 800 грн").

5. **`Order` и `OrderItem` (Заказы)**
   * **Суть:** Когда клиент выбрал нужные варианты из сметы и нажал "Оформить", создается `Order`.
   * **Поля:** `status` (статус доставки), `ttn_number` (накладная Новой Почты), `total_price` (сумма для клиента), `purchase_cost` (наша закупочная цена для подсчета маржи).

6. **`ChatMessage` (Чат)**
   * **Поля:** `message`, `sender_type` (кто отправил: клиент или менеджер), `attachment_url` (фото).

> **💡 Что такое relationship?**
> В SQLAlchemy строка `cars = relationship("Car", back_populates="owner")` означает, что мы можем получить все машины клиента, просто написав `client.cars`, и база данных сама сделает нужный JOIN-запрос!

## 🛡 4. Фильтрация данных (schemas.py)

Файл `backend/app/schemas.py` отвечает за то, в каком виде данные приходят от клиента и в каком уходят к нему. Мы используем библиотеку **Pydantic**.

**Почему схемы важны?**
Представьте, что мы ожидаем от фронтенда номер телефона. Если фронтенд пришлет букву "А", база данных может выдать ошибку. Чтобы этого не произошло, мы создаем схему `ClientCreate`. 

В схемах мы часто используем суффиксы для порядка:
* **`...Create` (напр. `CarCreate`)** — данные, которые нужны *только при создании* нового объекта. (ID еще нет).
* **`...Update` (напр. `CarUpdate`)** — данные, где все поля необязательные, так как мы можем изменить только одно поле (например, только пробег).
* **`...Response` (напр. `ClientResponse`)** — данные, которые сервер *отдает* фронтенду. **Важно:** В `ClientResponse` НИКОГДА нет поля `password`, чтобы случайно не отправить пароль хакерам.

## 📡 5. Маршрутизаторы (Routers)

В папке `backend/app/routers/` лежат контроллеры — они принимают запросы (GET, POST, PUT, DELETE) от фронтенда (JS) и вызывают нужные функции.

* **GET** — получить данные (список машин).
* **POST** — создать данные (отправить сообщение в чат).
* **PUT/PATCH** — обновить данные (сменить статус заказа).
* **DELETE** — удалить данные (удалить авто из гаража).

**Особый механизм FastAPI - `Depends(get_current_client)`:**
Почти в каждом роутере есть эта строчка. Это проверка авторизации. Функция проверяет заголовок запроса (Header) `X-Auth-Token`. Если токен верный, она сама находит клиента в базе и передает его в роутер. Если токен неверный или его нет — функция прерывает запрос и выдает ошибку 401 Unauthorized ("Токен не передан").

## 💻 6. Фронтенд (Как работает app.js)

На фронтенде мы используем стандартный браузерный JavaScript. 

### Основные концепции JS в этом проекте:
1. **`fetch()`** — главная функция для общения с сервером. Она отправляет асинхронный HTTP-запрос.
2. **`localStorage`** — маленькое хранилище внутри браузера. После успешного входа (Логина) мы получаем от сервера токен и сохраняем его: `localStorage.setItem('token', token)`. При всех последующих запросах мы достаем его и вкладываем в заголовки (`headers`).
3. **Генерация HTML (Template Literals)** — вы часто увидите код вроде:
   ```javascript
   container.innerHTML = data.map(car => `
       <div class="car-card">
           <h3>${car.brand} ${car.model}</h3>
       </div>
   `).join('');
   ```
   Это способ динамически отрисовать данные, полученные от сервера, прямо на веб-странице, не перезагружая её.

## 🔄 7. Жизненный Цикл: От Запроса до Заказа

Как устроена бизнес-логика нашего CRM, шаг за шагом:

1. **Запрос:** Клиент (в `client_frontend`) выбирает авто в гараже, нажимает нужную категорию (например, "Двигатель -> Свечи") и отправляет текстовый запрос. В базе создается `OrderRequest`.
2. **Уведомление менеджера:** В `admin_frontend` менеджер видит этот запрос в очереди. Менеджер может уточнять детали через чат (`ChatMessage`).
3. **Смета (Кошторис):** Менеджер нажимает "Скласти кошторис". Открывается окно, где менеджер заполняет `ProposalItem` (категория) и добавляет аналоги (Motul, Elf, оригинал) через `ProposalAlternative`. Данные отправляются на сервер.
4. **Выбор клиента:** Клиент видит красивую карточку сметы. Он выбирает радио-кнопками нужные аналоги по каждой позиции, выбирает способ оплаты и жмет "Оформить заказ".
5. **Заказ:** На сервере создается `Order`. В админке он падает во вкладку "Заказы". 
6. **Выполнение:** Менеджер собирает товар, делает фото, отправляет Новой Почтой. Он вводит ТТН и закупочную цену в админке. Статус заказа меняется на "Відправлено". Клиент видит ТТН.
7. **Аналитика:** На основе разницы между `total_price` (ценой для клиента) и `purchase_cost` (закупочной ценой) в админке автоматически считается чистая прибыль (Вкладка P&L).

## 🔒 8. Безопасность и Пароли

* **Хеширование паролей:** Все пароли перед сохранением в базу данных проходят криптографическое хеширование (через библиотеки `passlib` и `bcrypt`). Это значит, что никто (даже администратор, владелец бизнеса или создатель базы данных) не может увидеть или "подглянуть" оригинальный пароль клиента. Пароль превращается в строку вида `$2b$12$W2a...`, которую невозможно расшифровать. Восстановить утерянный пароль можно только через автоматическую процедуру сброса с помощью OTP-кода (Forgot Password).
* **Интерфейс:** Для удобства пользователей во всех полях ввода пароля добавлен функционал "глазок", позволяющий показать/скрыть вводимый текст. При регистрации пароль нужно вводить дважды (с валидацией на 100% совпадение) для защиты от опечаток.

## 🐞 9. Главные Советы для Новичка

* **Ошибки на фронтенде:** Если кнопка не нажимается или страница не грузится — открой Инструменты разработчика в браузере (клавиша **F12**). Перейди на вкладку **Console** (Консоль). Там красным текстом будет написана причина (например, опечатка в переменной).
* **Ошибки на бекенде:** Если в консоли браузера написано `500 Internal Server Error`, значит, фронтенд все сделал правильно, но код сервера (Python) упал. В этом случае иди в терминал, где запущен сервер (или логи Render), и читай `Traceback` (сообщение об ошибке) снизу вверх.
* **Документация API:** Запустив сервер локально, перейди по адресу `http://127.0.0.1:8000/docs`. FastAPI автоматически генерирует интерфейс (Swagger UI), где можно увидеть все доступные маршруты, посмотреть, какие данные они требуют, и даже протестировать их прямо из браузера!
* **Миграции БД:** Если ты добавил новое поле в `models.py` (например, `car.weight`), база данных автоматически не обновится, если таблица уже создана. Нужно либо удалить файл/базу и создать заново (для тестовой среды), либо использовать инструмент `Alembic` для миграций.
