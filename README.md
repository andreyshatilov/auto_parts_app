# 📚 Подробное Руководство Разработчика (Developer Guide)

Добро пожаловать в проект **«Міністерство Запчастин»**! Этот документ — ваш главный путеводитель по архитектуре, коду и бизнес-логике приложения по подбору автозапчастей. Он написан так, чтобы даже начинающий разработчик смог разобраться в том, как всё устроено.

---

## 🛠 1. Используемые Технологии (Стек)

Приложение разделено на две независимые части: **Frontend** (браузер) и **Backend** (сервер).

### Frontend (Клиентская и Админская части)
Без тяжёлых фреймворков (React, Angular). Всё на базовых технологиях:
* **HTML5** — разметка и структура интерфейса.
* **CSS3** — стили, цвета, анимации, адаптивная вёрстка (flexbox/grid).
* **Vanilla JavaScript (JS)** — логика: нажатия кнопок, отправка данных на сервер, переключение экранов.

### Backend (Серверная часть)
* **Python 3** — основной язык программирования.
* **FastAPI** — современный веб-фреймворк для создания REST API с автогенерацией документации (Swagger).
* **SQLAlchemy** — ORM (Object-Relational Mapping). Работаем с базой данных через объекты Python вместо сырых SQL-запросов.
* **Pydantic** — библиотека строгой валидации данных. Встроена в FastAPI.
* **PostgreSQL** — основная база данных (используется на Render в продакшене).
* **passlib + bcrypt** — криптографическое хеширование паролей.

### Деплой и Хостинг
* **Render.com** — облачный хостинг для бекенда (автоматический деплой (пиздеж, deploy latest commit каждый раз) из GitHub при каждом `git push` в `main`).
* **GitHub Pages / Netlify** — статический хостинг для фронтенда (или раздача через FastAPI `StaticFiles`).

## 🗄 3. База Данных (models.py)

В файле `backend/app/models.py` описана структура всех таблиц. SQLAlchemy автоматически переводит классы Python в таблицы PostgreSQL.

### Главные Таблицы:

| Таблица | Назначение | Ключевые поля |
|---------|-----------|---------------|
| **Client** | Учётная запись клиента | `phone`, `email`, `hashed_password`, `auth_token`, `is_verified` |
| **Car** | Автомобиль в гараже клиента | `vin`, `brand`, `model`, `engine_code`, `mileage`, `owner_id` |
| **OrderRequest** | Запрос на подбор запчастей | `client_id`, `car_id`, `category`, `description`, `status` |
| **Proposal** | Смета (ответ менеджера) | `request_id`, `status` |
| **ProposalItem** | Позиция в смете | `proposal_id`, `name`, `category` |
| **ProposalAlternative** | Вариант по позиции (аналог) | `item_id`, `brand`, `price`, `is_selected` |
| **Order** | Оформленный заказ | `status`, `ttn_number`, `total_price`, `purchase_cost` |
| **OrderItem** | Позиция в заказе | `order_id`, `alternative_id`, `quantity` |
| **ChatMessage** | Сообщение в чате | `message`, `sender_type`, `attachment_url` |

> **💡 Что такое `relationship`?**
> В SQLAlchemy строка `cars = relationship("Car", back_populates="owner")` означает, что мы можем получить все машины клиента, написав `client.cars`, — база данных сама выполнит нужный JOIN-запрос.

## 🛡 4. Валидация данных (schemas.py)

Файл `backend/app/schemas.py` определяет, в каком формате данные приходят от клиента и уходят к нему. Используется **Pydantic**.

**Зачем схемы?** Если фронтенд пришлёт букву «А» вместо номера телефона, сервер отклонит запрос с понятным сообщением об ошибке ещё ДО обращения к базе.

### Соглашения об именовании:
| Суффикс | Когда используется | Пример |
|---------|-------------------|--------|
| `...Create` | Создание нового объекта (ID ещё нет) | `CarCreate`, `ClientCreate` |
| `...Update` | Обновление (все поля необязательные) | `CarUpdate` |
| `...Response` | Ответ сервера клиенту (**без пароля!**) | `ClientResponse` |

## 📡 5. Маршрутизаторы (Routers)

В папке `backend/app/routers/` лежат контроллеры — они принимают HTTP-запросы от фронтенда и выполняют бизнес-логику.

| Метод | Действие | Пример |
|-------|----------|--------|
| `GET` | Получить данные | Список машин в гараже |
| `POST` | Создать | Отправить сообщение в чат |
| `PUT/PATCH` | Обновить | Сменить статус заказа |
| `DELETE` | Удалить | Удалить авто из гаража |

### Авторизация: `Depends(get_current_client)`
Почти в каждом роутере есть эта строчка. Это проверка авторизации. Функция проверяет заголовок `X-Auth-Token`. Если токен верный — находит клиента в базе и передаёт в роутер. Если нет — возвращает `401 Unauthorized`.

### Полный список роутеров:
| Файл | Ответственность |
|------|----------------|
| `auth.py` | Регистрация, логин по email/телефону, забытый пароль (OTP на email), сброс пароля |
| `cars.py` | CRUD автомобилей клиента (гараж) |
| `chat.py` | Сообщения между клиентом и менеджером |
| `clients.py` | Профиль клиента, список клиентов для админа |
| `requests.py` | Запросы на подбор запчастей |
| `proposals.py` | Формирование смет (кошторисів) менеджером |
| `orders.py` | Заказы: создание из сметы, статусы, ТТН |
| `invoices.py` | Счета / инвойсы |
| `payments.py` | Оплата заказов |
| `returns.py` | Возвраты товара |
| `transfers.py` | Внутренние переводы между складами |
| `analytics.py` | P&L аналитика: маржа, прибыль |
| `exports.py` | Экспорт данных в CSV/Excel |
| `crosses.py` | Кросс-номера (поиск аналогов по артикулу) |

## 💻 6. Фронтенд (app.js)

На фронтенде используется стандартный JavaScript без фреймворков.

### Ключевые концепции:

1. **`fetch()`** — отправка асинхронных HTTP-запросов к серверу.
2. **`localStorage`** — хранилище в браузере. После логина получаем токен от сервера и сохраняем: `localStorage.setItem('token', token)`. Все последующие запросы отправляются с заголовком `X-Auth-Token`.
3. **Template Literals** — динамическая генерация HTML:
   ```javascript
   container.innerHTML = data.map(car => `
       <div class="car-card">
           <h3>${car.brand} ${car.model}</h3>
       </div>
   `).join('');
   ```
4. **`togglePassword(btn)`** — универсальная функция «глазок» для переключения видимости пароля. Находит `<input>` внутри родительского `.password-wrapper` и меняет `type` между `password` и `text`.

## 🔄 7. Жизненный Цикл: От Запроса до Заказа

Бизнес-логика CRM, шаг за шагом:

1. **Запрос:** Клиент выбирает авто → категорию запчастей → описывает что нужно → создаётся `OrderRequest`.
2. **Уведомление:** Менеджер видит запрос в очереди в админ-панели. Может уточнить детали через чат.
3. **Смета:** Менеджер формирует `Proposal` с позициями (`ProposalItem`) и вариантами-аналогами (`ProposalAlternative`: Motul за 1000 грн / Elf за 800 грн / Оригинал за 1500 грн).
4. **Выбор:** Клиент видит карточку сметы, выбирает нужные варианты радио-кнопками, указывает способ оплаты → нажимает «Оформити замовлення».
5. **Заказ:** Создаётся `Order`. Менеджер видит его во вкладке «Заказы».
6. **Отправка:** Менеджер собирает товар, вводит ТТН Новой Почты и закупочную цену. Статус → «Відправлено». Клиент видит ТТН в кабинете.
7. **Аналитика:** Разница между `total_price` и `purchase_cost` = чистая прибыль (вкладка P&L в админке).

## 🔒 8. Безопасность и Пароли

* **Хеширование:** Все пароли хешируются через `passlib` + `bcrypt` перед сохранением в БД. Пароль превращается в строку вида `$2b$12$W2a...`, которую невозможно расшифровать обратно. Никто (включая владельца базы) не может посмотреть оригинальный пароль.
* **Сброс пароля:** Единственный способ восстановить доступ — через процедуру «Забули пароль?» → OTP-код на email → новый пароль.
* **Глазок (UI):** Во всех полях ввода пароля (логин, регистрация, сброс) есть кнопка показа/скрытия текста.
* **Подтверждение при регистрации:** Пароль вводится дважды с валидацией на 100% совпадение.
* **Требования к паролю:** Пароль может содержать только латинские символы, цифры и спецсимволы (ASCII). Это техническое ограничение алгоритма bcrypt для совместимости с различными версиями Python.
* **Токены:** После входа сервер генерирует уникальный `auth_token`, который хранится в `localStorage` браузера и отправляется в заголовке `X-Auth-Token` при каждом запросе.

## 🚀 9. Деплой на Render

### Как это работает:
1. Вы делаете `git push` в ветку `main` на GitHub.
2. Render автоматически подхватывает изменения и запускает билд.
3. Render устанавливает зависимости из `requirements.txt` и запускает сервер командой:
   ```
   uvicorn backend.app.main:app --host 0.0.0.0 --port $PORT
   ```

### Переменные окружения на Render:
| Переменная | Назначение |
|-----------|-----------|
| `DATABASE_URL` | Строка подключения к PostgreSQL |
| `ADMIN_PIN` | PIN-код для входа в админ-панель |
| `SMTP_*` | Настройки почтового сервера для отправки OTP |

### Частые ошибки при деплое:
* **`ModuleNotFoundError`** — забыли добавить библиотеку в `requirements.txt`.
* **`ImportError`** — имя класса в `schemas.py` не совпадает с тем, что импортируется в роутере.
* **Билд проходит, но сервер падает** — смотрите логи на Render, читайте `Traceback` снизу вверх.

## 🐞 10. Советы для Разработчика

* **Ошибки на фронтенде:** Нажмите **F12** → вкладка **Console**. Там будет причина ошибки.
* **Ошибки бекенда (500):** Читайте `Traceback` в логах Render или в терминале сервера. Ключевая строка — самая последняя.
* **Документация API:** Запустите сервер → откройте `http://127.0.0.1:8000/docs`. Swagger UI покажет все маршруты и позволит протестировать их в браузере.
* **Миграции БД:** При старте приложения (`main.py`) автоматически запускается скрипт проверки схемы базы данных. Он сам добавляет недостающие колонки (например `hashed_password`, `auth_token`, `shipping_address` и т.д.) через `ALTER TABLE`, если они отсутствуют, что обеспечивает отказоустойчивость при деплое на Render. Для сложных изменений (удаление/переименование колонок) всё ещё может потребоваться ручное вмешательство или Alembic.
* **Кеш браузера:** Если фронтенд не обновляется после деплоя — нажмите `Ctrl+F5` или обновите параметр `?v=` в теге `<script>` в `index.html`.
